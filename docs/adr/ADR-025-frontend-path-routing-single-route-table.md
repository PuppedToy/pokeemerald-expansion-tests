# ADR-025: The frontend's destinations are real paths, declared once in a shared route table

- **Status:** accepted
- **Date:** 2026-08-07
- **Task:** T-259

## Context

The app shell was a single-page app in the literal sense: every destination lived at `/`. The top nav was
`<button data-tab>` elements whose handler toggled a `.active` class, and the same pattern drove the
Features lists and the Feedback lists. Three things followed from that.

- Nothing was addressable. There was no way to link to Features, let alone to one of its lists, and no way
  to send someone to the Randomizer.
- Nothing was indexable. A crawler saw buttons, not links, so the site had no internal link graph and
  exactly one URL.
- The browser's own navigation was broken. Back/forward, open-in-new-tab, copy-link and reload-in-place
  all fail when the destination is never in the URL.

The constraints on any fix: the app is served by Express behind Caddy (which only reverse-proxies, so
routing is entirely an Express concern); production serves a minified `frontend/dist` shell that shadows
the source; and the frontend test harness is a zero-dependency DOM stub (ADR-009), which cannot exercise
`history`/`location`.

## Decision

**Every destination has a real path, and the map of paths lives in exactly one module.**

1. `frontend/js/router.js` is the site's URL map and its only home: the route table plus `parsePath`,
   `pathFor`, `titleFor`, and the two derived path lists. It is pure — no DOM, nothing executed at load —
   so both the browser and Node import the same table. `backend/server.js` importing the frontend's own
   route table is what makes "navigable in the browser but 404 on reload" unrepresentable.
2. **Paths, not hashes.** `/features`, `/features/docs`, `/randomizer`. The server answers the app shell
   for the paths that table declares.
3. **A fixed list, never a catch-all.** An unknown path keeps 404-ing. A blanket fallback would turn every
   typo, every asset a build forgot and every unmatched `/api` call into `200` plus a page of HTML.
4. **The nav is anchors.** `<a href="/features">`, and the click handler only intercepts the plain
   left-click on a path the router resolves. Modifier-clicks, middle-clicks, downloads, `#` action links,
   external links and the standalone legal pages are left entirely to the browser.
5. **One canonical URL per destination.** A tab's first list is canonically the bare tab path (`/features`,
   not `/features/rom`), so the default list is not two URLs. Alias forms (`/features/rom`, `/home`) still
   resolve — a shared link must not rot — but nothing links to them and the client rewrites them to the
   canonical form with `replaceState` on arrival.
6. **URL-driven sub-navigation is a `<nav>` of links with `aria-current`, not an ARIA tablist.** Once each
   list has its own address, announcing it as a tab misdescribes what activating it does.

`/robots.txt` and `/sitemap.xml` are generated by Express from the same table plus `BASE_URL`, because a
static file would have to hardcode the domain.

## Alternatives considered

- **Hash routing (`#/features`).** No server change at all, but hash fragments are not sent to the server,
  are weak for indexing, and `/features` is what the owner (and anyone else) expects to type.
- **A catch-all `*` → index.html.** One line instead of a list, at the cost of every 404 becoming a 200 —
  which hides exactly the broken-asset and broken-API-route failures worth seeing.
- **Restating the path list in `server.js`.** Two homes for one fact; the drift shows up as a destination
  that works until it is reloaded.
- **Keeping buttons and adding `pushState` to their handlers.** Fixes the URL but not indexability, and
  still no open-in-new-tab or copy-link — the mechanisms the browser already provides for free with an
  `href`.
- **Server-rendering a distinct `<title>`/canonical per route.** Deferred: titles are set client-side and
  crawlers execute JS. If indexing evidence says otherwise, injecting them at send time is a contained
  change behind the same route table.
- **Putting the wizard's 3 steps in the URL.** Rejected: a step is the state of an in-progress run held in
  memory, so a step-2 URL would mean nothing in a fresh tab.

## Consequences

- Adding a destination is one entry in the route table; the server, the sitemap and the tests follow from
  it. Adding one anywhere else does not work, which is the point.
- The nav's behaviour is the browser's, not ours: we maintain the interception rules (which clicks to let
  through), not a navigation implementation.
- Routing behaviour that the zero-dep stub cannot reach — cold-load deep links, no-reload navigation,
  back/forward, alias normalisation — is covered by `visual-tests/routing.spec.mjs` in a real browser, per
  ADR-010's split. The route table itself stays unit-tested.
- Two facts are now load-bearing for anyone touching this: paths must resolve through `router.js` (not be
  hardcoded), and the standalone pages (`privacy.html`, `terms.html`, `verify.html`, `reset.html`) stay
  outside the table — `verify`/`reset` in particular are baked into already-sent emails.
