# T-259 — Give the frontend real URLs and indexable links

## Context

The app shell is a single-page app where every destination lives at `/`. Navigation is a set of
`<button data-tab>` elements whose click handler toggles a `.active` class (`frontend/js/app.js`
`setActiveTab`/`setActiveSubtab`); the same pattern drives the Features lists (`.subtab`) and the
Feedback lists (`.fb-tab`).

Consequences the owner asked to fix:

- **No addressable destinations.** Features is not `/features`, the Randomizer is not `/randomizer`,
  and a Features list cannot be linked at all.
- **Nothing is indexable.** A crawler sees buttons, not links, so there is no link graph and only one
  URL for the whole site.
- **Browser navigation is broken.** Back/forward, "open in a new tab", copy-link and reload-in-place
  do not work, because the destination is never in the URL.

Related: the routes must keep working through the minified production shell
(`buildFrontendDist.cjs` → `frontend/dist`, mounted ahead of source by `backend/server.js`), and the
frontend is tested with the zero-dep DOM stub (ADR-009), so the routing decisions belong in a pure
module rather than inline in `app.js`.

## Plan

One route table as the single home for "what URLs exist", consumed by both sides:

1. **`frontend/js/router.js`** (new, pure, no DOM at import time) — the route table plus
   `parsePath(pathname)` → `{ tab, subtab }` and `pathFor(tab, subtab)` → pathname, and the list of
   paths the server must serve the shell for. Unit-tested in isolation.
2. **`backend/server.js`** imports that path list and serves the app shell (dist or source, mirroring
   `SERVE_DIST`) for each known route. Unknown paths keep 404-ing — no blanket catch-all, so a
   missing asset or a stray `/api/*` never silently returns HTML.
3. **`frontend/index.html`** — nav tabs, Features lists, Feedback lists, the brand and the landing CTA
   become real `<a href="/…">` anchors carrying their existing `data-*` hooks.
4. **`frontend/js/app.js`** — one `navigate()` path: anchor clicks `pushState` (letting
   ctrl/cmd/middle-click fall through to the browser), `popstate` restores, and the initial state comes
   from `location.pathname`. Per-route `document.title` so the routes are distinguishable when indexed.
5. **`/robots.txt` + `/sitemap.xml`**, generated by Express from the same route table plus `BASE_URL`
   (a static file would have to hardcode the domain), so the new URLs are actually discoverable.

Deliberately **out of scope**:
- The Randomizer wizard's 3 steps stay out of the URL — they are the state of an in-progress run (a
  generated bundle in memory), not addressable pages, and a step-2 URL would be meaningless in a fresh
  tab. Same for the auth and presets modals.
- The standalone legal pages (`privacy.html`, `terms.html`) keep their URLs. They are already ordinary
  crawlable pages with a real address each — the `.html` suffix is cosmetic, and renaming them would
  churn the T-222 legal-notices test for no navigational gain. `verify.html` / `reset.html` are
  likewise untouched: those URLs are baked into already-sent emails (`server.js`
  `verifyUrl`/`resetUrl`).

Acceptance criteria:
- [x] `/features`, `/randomizer`, `/feedback`, `/settings`, `/admin` and `/` each render their section
      directly on load and on reload; `/` is home.
- [x] Every Features list is addressable (`/features/rom`, `/features/randomizer`, `/features/docs`),
      as is every Feedback list; `/features` renders the first list.
- [x] Nav, Features/Feedback lists, brand and landing CTA are `<a href>` anchors with the real path —
      crawlable, ctrl/cmd-clickable into a new tab, right-click-copy-link-able.
- [x] Back/forward moves between visited destinations; the active tab always matches the URL.
- [x] An unknown path (e.g. `/nope`) still 404s, and `/api/*` behaviour is unchanged.
- [x] Every route carries its own `<title>`.
- [x] `cd frontend && npm test`, `cd backend && npm test` and `cd randomizer && npm test` green, with
      new tests covering the route table, the anchors in the HTML, and the server's route serving.

## Outcome

Shipped. The frontend has real URLs and a nav made of links.

**What shipped**
- `frontend/js/router.js` — the site's URL map and its only home: the route table plus `parsePath` /
  `pathFor` / `titleFor`, `SHELL_PATHS` (every path the server must answer) and `CANONICAL_PATHS` (one per
  public destination). Pure, so `backend/server.js` imports the same table.
- `backend/shell/routes.js` — serves the shell for those paths (dist-or-source per request, mirroring the
  static mounts), plus generated `/robots.txt` and `/sitemap.xml`. A fixed list, not a catch-all.
- `index.html` / `app.js` / `feedback.js` — anchors throughout, one delegated click handler, `popstate`,
  per-route `document.title`, `aria-current`. `feedback.js`'s duplicate `.fb-tab` wiring deleted.
- **ADR-025** records the decisions; `docs/INDEX.md` lists it.

Destinations: `/`, `/features` (+ `/features/randomizer`, `/features/docs`), `/randomizer`, `/feedback`
(+ `/feedback/bugs`), `/settings`, `/admin`.
